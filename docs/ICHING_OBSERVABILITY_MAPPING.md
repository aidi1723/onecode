## 1. 架构红线声明 (The Architectural Red Line)

> [!CAUTION]
> **观测隔离红线**：
> 本文列出的所有高级卦象计算（包括动爻、十二消息卦、承乘比应、大衍比例、互卦和交卦）的返回值**只能且必须只进入 Evidence 或 Trace 日志**，作为纯粹的观测指标（Observability / Telemetry）。
> 
> `sandbox.py`、`verifier.py`、`execution_engine.py` 和 `runner.py` 的内部核心控制流分支**绝对不可**读取这些高级观测指标。系统绝不能因为偏离大衍基线、或者互卦陷入震荡，而去改写执行计划、改变回滚决策或触发系统停机。

## 2. 易经数学公式与软件工程映射

### 2.1 动爻 (Moving Lines)

**数学定义**：
动爻表示两个状态之间的按位差异。计算两卦的异或（XOR），结果为 1 的位即为动爻。
- `moving_lines(base, current) = [i for i in range(6) if ((base XOR current) >> i) & 1]`

**软件映射 (Software Mapping)**：
- 代表系统状态在两个迭代/时间步之间的**增量变化（State Transitions）**。
- 例如：内存 RSS 跨越阈值、某个测试用例从 failed 变为 passed、网络连接从断开变为连接。
- 在日志中，动爻的数量反映了系统的“动荡程度”（Volatility）。

### 2.2 承乘比应 (Micro Relations / Cheng, Sheng, Bi, Ying)

**数学定义**：
基于六爻中相邻和对应位置的关系（$b_0$ 为初爻，自下而上计算）：
- **乘 (Cheng)**：上阳下阴（$b_i=0, b_{i+1}=1$），阳气压迫阴气。
- **承 (Sheng)**：上阴下阳（$b_i=1, b_{i+1}=0$），阴气承托阳气。
- **比 (Bi)**：相邻同性（$b_i = b_{i+1}$），极性相同。
- **应 (Ying)**：内外卦对应爻极性相异（$b_i \neq b_{i+3}$ 对于 $i \in \{0, 1, 2\}$）。

**软件映射 (Software Mapping)**：
- **乘/承 (Cheng/Sheng)**：反映了系统局部的**结构应力（Structural Stress）**。例如上层服务资源竞争压迫底层服务（乘），或底层依赖稳定支撑上层调用（承）。
- **比 (Bi)**：代表**局部动量连续性**。大量相邻态一致说明系统处于平稳的连续阶段，但也可能暗示死循环。
- **应 (Ying)**：代表**跨层协同（Cross-Layer Coordination）**。内卦（底层/执行器）与外卦（上层/校验器）状态相反互补，说明系统具备良好的交互与反馈循环。

### 2.3 十二消息卦 (12 Sovereign / Tidal Hexagrams)

**数学定义**：
代表阴阳消长的十二个标准状态，按周期循环：
`["复", "临", "泰", "大壮", "夬", "乾", "姤", "遁", "否", "观", "剥", "坤"]`
- `cycle_phase(count) = SOVEREIGN_HEXAGRAMS[count % 12]`

**软件映射 (Software Mapping)**：
- 反映 Agent 或后台任务的**宏观生命周期（Macro-Lifecycle）**。
- 从“复”（初始化/探底回升）到“乾”（满载/高并发），再到“姤”（出现阻力/衰退），最后到“坤”（休眠/重置）。
- 记录在 Trace 中，用于监控长期后台任务（如大规模数据清洗）是否健康推进，还是在某个阶段过早枯竭。

### 2.4 大衍比例 (Da Yan Proportions & 25% Baseline)

**数学定义**：
大衍之数生成的四象理论概率：
- 老阳（动）：3/16 (18.75%)
- 老阴（动）：1/16 (6.25%)
- 动爻总比例基线（Volatility Baseline）：**25%**

**软件映射 (Software Mapping)**：
- 这是极佳的**系统熵值与随机性指标（System Entropy & Baseline Deviation）**。
- 大规模并发日志或 LLM 采样探索过程中，状态变化的频率应向 25% 回归。
- 如果偏离 25%：
  - 过低（如 <5%）：系统陷入僵化，LLM 输出重复，或资源死锁。
  - 过高（如 >60%）：系统处于剧烈震荡、路由翻锅或内存 thrashing 状态。
- **牢记红线**：即便发生严重偏离，此指标仅作监控大盘对照，绝对不可直接阻断执行流程。

### 2.5 互卦 (Hu Gua / Mutual Hexagrams)

**数学定义**：
提取原卦内部蕴含的深层结构。丢弃初爻（$b_0$）和上爻（$b_5$）。
- 新内卦：$b_1, b_2, b_3$
- 新外卦：$b_2, b_3, b_4$
- 互卦生成定理：最多经过 2 次迭代，互卦必定落入以下数学吸引子：
  - 纯态吸引子：`{坤 0, 乾 63}`
  - 2-循环震荡吸引子：`{既济 21 ↔ 未济 42}`

**软件映射 (Software Mapping)**：
- 代表系统的**潜藏趋势或内在动力（Latent Drivers & Attractors）**。
- 如果互卦迅速收敛到纯态（坤/乾），表示当前任务的核心动机是明确且同质的（单纯的建设或销毁）。
- 如果落入 `{既济 ↔ 未济}` 的 2-循环，代表系统内部存在固有的对立或交替（如生产者-消费者队列的满与空）。
- **警告**：不要把互卦陷入 `{既济 ↔ 未济}` 的 2-循环误判为业务逻辑死锁（Deadlock）。这是一个自然数学吸引子，属于正常规律。

### 2.6 交卦 (Jiao Gua / Intersecting Hexagrams)

**数学定义**：
内外卦位置互换。
- 原卦：$T_{out} \text{ over } T_{in}$
- 交卦：$T_{in} \text{ over } T_{out}$

**软件映射 (Software Mapping)**：
- 代表**视角反转或主客体换位（Perspective Inversion）**。
- 在微服务调用中，交卦代表从被调用方反观调用方。
- 在 OneCode 内部，交卦可用于分析 Validator（校验器，通常居上）与 Executor（执行器，通常居下）冲突时，如果双方身份反转，局势的演变方向。它提供了一种不中断网络的“思想实验”逃生通道日志，用于事后分析，不在冲突时实时改计划。

## 3. 观测系统的最佳实践

为了维护 OneCode 的健壮性，请开发者在贡献代码时遵循以下准则：

1. **分离观测与控制**：始终将上述易经运算置于 `IchingProfileMixin` 或专属的监控侧，由 Logger 异步记录，确保不增加主控循环（如 `run_model_task`）的复杂度和不可测性。
2. **作为数据湖对照**：日志应当被收集并投递到数据湖，与系统监控（Grafana/Prometheus）对齐，通过时间序列对比大衍基线（25% 动爻率）。
3. **不做解码先验**：不要将这些复杂的数学规律作为 LLM 结构化输出解码（如 Yizijue Logits）的先验惩罚。解码层只看合法性和基本的安全性，严禁引入互卦等深层逻辑进行剪枝。
