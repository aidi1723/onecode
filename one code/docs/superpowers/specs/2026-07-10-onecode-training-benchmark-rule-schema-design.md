# OneCode Training and Benchmark Rule Schema Design

## Goal

Make persisted training, corpus, evaluation, and benchmark records
self-describing when they contain or derive from a six-bit I Ching state,
without modifying the kernel transition formula or the strict model Action JSON
contract.

## Confirmed Boundary

This phase is a projection and evidence-contract change, not a core algorithm
change.

- Do not modify `IchingKernel.transition()` or dispatch behavior.
- Do not add confidence, priority, retry authority, or parallel policy state.
- Do not add `rule_schema` inside the strict Action JSON generated by
  `assistant_payload()`.
- Do not reinterpret or rewrite historical training artifacts in place.

## Foundation Invariants

Every exported state remains the direct projection of the existing bottom
theory and formulas:

```text
six yin/yang line bits
-> inner and outer trigrams
-> five-element generation/control relation
-> yin/yang pressure and dynamic balance
-> existing transition and dispatch
```

`rule_schema` may identify how the six bits name Li and Xun, but it may not
create a state, change a line, alter a five-element relation, rebalance a
profile, or override a transition. Training and benchmark records must copy the
schema and status produced by the kernel rather than recomputing an alternative
result.

## Record Contract

New persisted records use `ACTIVE_RULE_SCHEMA`, currently
`onecode-iching-v2`.

The following records carry top-level `rule_schema`:

- gateway training JSONL rows;
- YiZiJue-LM corpus and evaluation rows;
- YiZiJue-LM state-basis rows;
- benchmark reports;
- benchmark A/B comparison reports.

The schema belongs to the persisted record, not the Action JSON payload. This
keeps extracted JSONL rows self-describing while preserving the model output
grammar.

## Compatibility

- Missing `rule_schema` is accepted as historical `onecode-iching-v1`.
- Unknown schemas fail closed.
- New builders and writers always emit the active schema.
- Validators return normalized records so downstream readers receive an
  explicit schema even when loading legacy rows.
- A state-basis row must use the same schema at its record and basis layers if
  basis-level schema metadata is present.

## Validation

- `rule_schema` must be a known immutable schema identifier.
- Existing six-bit state validation remains authoritative.
- Action JSON remains limited to `facts`, `yizijue_state`, `action`, and
  `reason`.
- Benchmark report schema identifies the meaning of all embedded OneCode
  runtime status codes.

## Acceptance Criteria

1. New training and YiZiJue-LM rows emit v2 schema metadata.
2. Legacy rows without metadata validate as v1.
3. Unknown schema metadata is rejected.
4. Action JSON structure remains byte-for-byte field compatible.
5. Benchmark and A/B reports emit active schema metadata.
6. Existing transition, dispatch, and safety tests remain unchanged and pass.
7. Exported state, trigram, element, pressure, transition, and dispatch fields
   remain equal to the corresponding `IchingKernel.cross_cutting_profile()`
   result under the same schema.
